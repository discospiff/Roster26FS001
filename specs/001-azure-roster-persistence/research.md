# Azure Roster Persistence Research

## Decision: Use a storage abstraction with environment-selected implementations

- **Decision**: Keep the existing in-memory store for local and Visual Studio execution and add a MySQL-backed store for Azure execution behind the same application-facing storage contract.
- **Rationale**: The Index page must not know which environment or database is active. This preserves current local behavior and makes both storage modes testable.
- **Alternatives considered**: Embedding environment checks and SQL calls directly in the Razor Page was rejected because it couples presentation logic to deployment and makes failure handling harder to test.

## Decision: Use MySQL In App through `MYSQLCONNSTR_localdb`

- **Decision**: Azure storage configuration comes from the `MYSQLCONNSTR_localdb` environment variable. The application must treat the variable as an Azure-only dependency.
- **Rationale**: This is the connection variable specified for the Azure App Service MySQL In App deployment. Local execution must not contact the database even if unrelated configuration values exist.
- **Alternatives considered**: Azure SQL, Cosmos DB, Azure Table Storage, and a separately provisioned MySQL server were rejected for this feature because the selected deployment target is MySQL In App.

## Decision: Normalize the Azure In App connection string before opening a connection

- **Decision**: Parse the Azure-provided connection string as key/value connection-string data, map its Azure-specific keys to the MySQL client syntax, and preserve the generated host, user, password, database, and port values. The normalized result must be validated before use.
- **Rationale**: MySQL In App does not use a fixed port. The port embedded in `MYSQLCONNSTR_localdb` is authoritative and must be retained. Assuming 3306 can produce socket or connection failures.
- **Alternatives considered**: Passing the environment value through unchanged was rejected because Azure's connection-string key names may not match the selected MySQL client library's canonical syntax. Hard-coding 3306 was rejected because the assigned port is generated by Azure.

## Decision: Use a supported ADO.NET MySQL client with minimal data-access layering

- **Decision**: Use a maintained MySQL ADO.NET provider and parameterized commands for the small roster data set. Keep provider-specific code inside the Azure persistence implementation and connection-string normalizer.
- **Rationale**: The application has a simple entity and does not require a full ORM or migration framework to meet the feature requirements. ADO.NET keeps the dependency surface focused while supporting asynchronous I/O.
- **Alternatives considered**: Adding an ORM was rejected for this small schema unless implementation requirements later demonstrate a need for change tracking or migrations.

## Decision: Provision schema idempotently

- **Decision**: The Azure persistence initialization path must create or validate the roster table safely when the application starts, without deleting existing data. Schema changes must be versioned and reviewed as part of deployment planning.
- **Rationale**: MySQL In App requires a usable table after deployment and must retain entries across restarts and redeployments.
- **Alternatives considered**: Requiring a manual one-time database script was rejected as the sole mechanism because it increases deployment drift and makes fresh environments harder to validate.

## Decision: Fail safely on Azure persistence errors

- **Decision**: A failed Azure read or write must be logged with safe diagnostic context, must not be reported as a successful save, and must not silently fall back to the in-memory store for the failed operation. User-entered values should remain available for retry where the page flow permits.
- **Rationale**: Silent fallback would create data loss and inconsistent behavior between application instances.
- **Alternatives considered**: Best-effort memory fallback was rejected because the specification requires Azure persistence to be authoritative in Azure.

## Decision: Test normalization and environment selection without requiring Azure

- **Decision**: Unit tests must cover connection-string normalization, generated-port preservation, malformed configuration, and storage-mode selection. Local tests must use the in-memory store. MySQL integration tests must be opt-in and require an explicitly configured test database.
- **Rationale**: CI and Visual Studio must remain independent of Azure resources while the parsing and selection logic remains fully verified.
- **Alternatives considered**: Requiring a live Azure MySQL In App instance in every test run was rejected because it would make normal development and pull-request validation unreliable.
